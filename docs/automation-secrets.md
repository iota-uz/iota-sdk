# Секреты автоматизаций: встроенный коннектор «Secret»

Секреты вида `API_KEY` арендатор ведёт на странице «Интеграции» как встроенный коннектор «Secret».
Запись секрета (имя, описание, ссылка на значение, версии, времена создания, ротации и последнего
использования) лежит в `automation.secrets`; **значение** лежит за портом хранилища
(`pkg/automation/secrets`). Страница и ноды видят только запись; значение после сохранения не показывается.

## Порт хранилища

```go
type Writer interface {
    Put(ctx, ref Ref, data map[string]string) (Metadata, error) // следующая версия значения
    Delete(ctx, ref Ref) error                                  // со всеми версиями; нет значения - не ошибка
    Prune(ctx, ref Ref, keepFrom int) error                     // удалить версии до keepFrom
    List(ctx, root Ref) ([]string, error)                       // пути со значениями под префиксом root.Path
}
type Reader interface{ Read(ctx, ref Ref) (Value, error) }                // версия ref.Version (0 - последняя) целиком
type MetadataReader interface{ Metadata(ctx, ref Ref) (Metadata, error) } // версии и времена, не значение
type Store interface{ Writer; Reader; MetadataReader }
```

`Ref{TenantID, Path, Version}` - где лежит значение; `Version` выбирает версию для `Read` (0 - последняя). Путь формирует `Locator`; по умолчанию
`DefaultLocator(prefix)`: `<prefix>tenants/<tenant>/automation/secrets/<secret-id>` (prefix - окружение,
например `prod/`). Запись хранит `ref_path`, так что смена Locator не ломает уже созданные секреты.

Процесс может держать только `Writer` (управление) или только `Reader` (резолв в нодах): композиция
выдаёт каждому потребителю его часть.

### Контракт адаптера

- Значения версионируются как в KV v2: `Put` добавляет следующую версию, прежние остаются до `Prune`.
- `Read` возвращает одну версию целиком, никогда поля двух версий (у встроенного адаптера - одна строка и один запрос).
- `Put` виден следующему `Read` в любом процессе; кеша, переживающего ротацию, нет. Версия растёт атомарно.
- `Ref` без арендатора - `ErrForbidden`; путь чужого арендатора - `ErrNotFound`/`ErrForbidden`, значение не отдаётся.
- Недоступность хранилища, неподходящий ключ, повреждённая строка - `ErrUnavailable`. Вызывающий **никогда** не
  подменяет её переменной окружения или устаревшим значением.
- Ошибки не содержат значений.

## Встроенный адаптер

`connectors.NewSealedSecrets(db, keys)` хранит значение в `automation.secret_values`
(`tenant_id, path, version, key_id, nonce, ciphertext`, PK `(tenant_id, path, version)`): AES-256-GCM тем же кольцом
ключей, что и подключения; AAD связывает шифртекст с арендатором, путём и версией. Без кольца ключей
каждый вызов - `ErrUnavailable`, оборачивающий `connectors.ErrNotConfigured`. `Store.Rewrap` пере-шифровывает
значения секретов вместе с подключениями.

## Менеджер и резолвер

- `secrets.NewManager(db, writer, meta, locator)`: `List`, `Create`, `Update` (имя, описание; с проверкой версии),
  `Rotate` (новая версия значения), `Delete` (значение и запись). Значение - не пустое, до 64 КиБ; имя -
  `^[A-Z][A-Z0-9_]{0,63}$`, уникально среди живых секретов арендатора (`ErrNameTaken`).
- **Протокол без удерживаемых соединений.** Ни один шаг не держит транзакцию (и соединение пула), пока
  пишется значение: хранилище может брать соединения из того же пула (встроенный адаптер так и делает), и
  пул из одного соединения иначе ждал бы сам себя. Состояние записи после любого сбоя говорит, что опубликовано:
  - *подготовлена*: `value_version = 0` - имя занято, никто её не читает, значение может быть или не быть;
  - *опубликована*: `value_version = N > 0` - читатели читают версию N;
  - *надгробие*: `deleted_at` - имя свободно, значение удаляется.
- **Заявка на запись.** Перед вызовом `Writer.Put` менеджер одним оператором отмечает запись
  (`value_write_at`). Надгробие хранится, а его значение удаляется заново при каждом `purge`, пока последняя
  заявка не старше окна записи (10 минут). Поэтому значение, записанное после удаления (ротация, которую обогнал
  `Delete`, или процесс, остановившийся сразу после записи), всегда находится по надгробию и удаляется.
- **Срок записи (fence).** `Ref.NotAfter` - момент, после которого адаптер не должен начинать или фиксировать
  версию; менеджер ставит его в заявку + половину окна (по часам БД). Встроенный адаптер проверяет его в самом
  вставляющем операторе. Решение снять надгробие принимается **до** удаления значения: только если заявка тогда
  уже истекла и с тех пор не менялась. Срок лишь сужает окно гонки - гарантией не служит: хранилище может
  задержать уже начатую запись (оператор PostgreSQL, запрос к OpenBao, который клиент не может отменить).
- **Подметание (sweep) - гарантия.** Каждый `purge` перечисляет значения под корнем арендатора
  (`Locator.Root`, `Writer.List`) и удаляет те, что не названы ни живой, ни подготовленной записью. Сначала
  читается список хранилища, потом записи: создание вставляет подготовленную запись до записи значения,
  поэтому значение живого или создаваемого секрета не трогается. Запись, зафиксированная сколь угодно поздно
  (даже после удаления секрета и снятия надгробия), находится в списке хранилища и удаляется следующим
  подметанием: ссылка для очистки — само хранилище. Под корнем нельзя хранить ничего постороннего; пустой
  корень менеджер отвергает.
  **Смена корня (префикса Locator).** Уже созданные секреты читаются по сохранённому `ref_path`, но подметание
  смотрит только под текущий `Root`. Поэтому при смене префикса (например, `prod/` → `prod-v2/`) старый корень
  нельзя бросать сразу: до переключения дождитесь, чтобы у старого корня не осталось надгробий и заявок моложе
  окна записи (10 минут), и после переключения продолжайте подметать старый корень (`Locator.Root` композиции,
  возвращающий старый префикс, на время переходного периода или разовый проход по `Writer.List(старый корень)`
  с удалением путей, которых нет среди `ref_path` живых записей), пока под ним не останутся только значения
  живых секретов.
  Путь значения принадлежит одному секрету навсегда: `Locator.Locate` обязан класть его под `Root` и включать
  id нового секрета (менеджер отказывает в создании иначе, уникальный индекс `(tenant_id, ref_path)` страхует),
  поэтому подметание никогда не удалит значение более позднего секрета по переиспользованному пути. У надгробий
  и у подметания - свои сроки; надгробие, на котором хранилище падает, уходит в конец очереди, а подметание
  продолжает с пути, на котором остановилось прошлое, - падающие записи не задерживают остальные.
- **`Put` возвращает свою версию**: ровно ту, что записал этот вызов, даже если параллельный `Put` уже добавил
  следующую; менеджер публикует только то, что записал сам.
- **Create**: вставить подготовленную запись → `Writer.Put` → опубликовать (`value_version = 1`). При ошибке
  менеджер перечитывает запись: опубликована (ответ на COMMIT потерян) - это успех, значение не трогается;
  подготовлена - одним оператором становится надгробием (опубликовать её уже нельзя, имя свободно), затем
  удаляется значение, а надгробие хранит ссылку, пока значение не удалено; записи нет - значение сирота и
  удаляется. Подготовленные записи старше 10 минут `purge` так же превращает в надгробия.
- **Rotate**: заявка на запись (запись должна быть живой) → `Writer.Put` (версия N+1) → одним оператором
  опубликовать с проверкой версии записи; из двух параллельных ротаций публикует одна, вторая получает
  `ErrVersionConflict`. Если запись за это время удалили, ротация сама удаляет записанное значение
  (а если не успела - его найдёт `purge`). Сбой между записями оставляет запись и читателей на N, а UI видит ошибку; потерянный ответ
  сверяется по записи. После публикации удаляются версии до предыдущей (`Prune(N)`): версия N остаётся для
  читателей, которые нашли запись перед ротацией.
- **Delete**: одним оператором надгробие (имя сразу перестаёт разрешаться и освобождается), затем значение и
  строка. Если хранилище недоступно, надгробие остаётся, и любой следующий вызов менеджера для арендатора
  (`purge`) повторяет удаление.
- `secrets.NewResolver(db, reader)`: `Has(ctx, tenant, name)` - только по записям, без чтения значения и
  отметки использования; `Resolve(ctx, tenant, name)` читает опубликованную версию (`value_version`). Если точной версии нет, резолвер
  перечитывает запись: ротация успела опубликовать новую и удалить старую - читает новую (до 3 попыток);
  запись не изменилась - `ErrUnavailable`. Нет
  записи - `ErrNotFound`; сбой записей или хранилища - `ErrUnavailable`. Значение читается при каждом вызове, поэтому ротация действует в
  работающем процессе без перезапуска. `last_used_at` обновляется не чаще раза в минуту и не может
  провалить чтение.

## Порядок разрешения имени в ноде

Нода (Code, HTTP) объявляет секреты по имени. `access.ChainSecrets` ищет:

1. секрет арендатора (коннектор «Secret»). Сначала `Has` по записям; если имя принадлежит арендатору, субъект,
   от имени которого идёт запуск, должен иметь `Secrets.Use` - иначе нода падает с кодом `secret_forbidden`,
   а значение не читается и использование не отмечается. Только после этого `Resolve`;
2. цепочка приложения (`access.FromResolver`): `CONNECTION__FIELD` - секретное поле подключения, затем
   `host.SecretResolver`. Поле с `"x-authorization-only": true` (токен и пароль коннектора HTTP/API) так не
   отдаётся никогда: им пользуется только авторизация самого подключения;
3. иначе код `secret_missing`, сообщение `unknown secret NAME`.

`ErrUnavailable` хранилища арендатора - управляемая ошибка `unavailable` (повторяемая); к цепочке приложения
в этом случае **не** переходим.

## RBAC

- `Secrets.Manage` - создавать, переименовывать, ротировать, удалять (набор прав `secrets_manage`);
- `Secrets.Use` - автоматизации пользователя читают секреты арендатора (набор `secrets_use`);
- `Connections.Use` - автоматизации пользователя вызывают подключения арендатора из Code и HTTP нод
  (`env.connections`, `auth: {connection}`): и HTTP-запросы, и Go-операции (набор `connections_use`). Без него
  нода получает `permission_denied` до обращения к провайдеру. Перед каждым вызовом статус подключения
  читается заново: выключенное или сломанное за время запуска подключение даёт `connection_disabled` /
  `connection_broken`, провайдер не вызывается.
- **Обновление.** До этого изменения в SDK не было ни одного `CodeAccessor`, поэтому Code и HTTP ноды на
  встроенных коннекторах подключениями не пользовались. Приложение, которое само зарегистрировало коннектор с
  `CodeAccessor` (`automations.WithConnectors`), должно при обновлении выдать `Connections.Use` (набор
  `connections_use`) ролям, от имени которых работают его автоматизации; иначе такие ноды получат
  `permission_denied`.

## Заменить адаптер

```go
composition.Provide[secrets.Store](b, func(c *composition.Container) (secrets.Store, error) {
    return myopenbao.New(...), nil // Writer + Reader + MetadataReader
})
```

Менеджер, резолвер и Locator собираются поверх `secrets.Store`, записи остаются в PostgreSQL.

## Следующий шаг: адаптер OpenBao KV v2 (#1382)

| Порт | KV v2 (mount `secret`) |
| --- | --- |
| `Put(ref, data)` | `POST /v1/secret/data/<ref.Path>` с `{"data": {...}, "options": {"cas": <версия>}}`; версия из ответа - `Metadata.Version`. `ref.NotAfter`: не отправлять запрос после срока (запоздавшую запись, которую уже не отменить, уберёт подметание) |
| `List(root)` | `LIST /v1/secret/metadata/<root.Path>` (рекурсивно по подпапкам) |
| `Read(ref)` | `GET /v1/secret/data/<ref.Path>?version=<ref.Version>` (без параметра при 0) - версия целиком (`data.data`, `data.metadata.version`); 404 - `ErrNotFound` |
| `Metadata(ref)` | `GET /v1/secret/metadata/<ref.Path>` - `current_version`, `created_time`, `updated_time` |
| `Delete(ref)` | `DELETE /v1/secret/metadata/<ref.Path>` - все версии; 404 не ошибка |
| `Prune(ref, keepFrom)` | `POST /v1/secret/destroy/<ref.Path>` с `{"versions": [1..keepFrom-1]}` |

Политики разделены: роль записи (`create`, `update` на `secret/data/tenants/*/automation/secrets/*`,
`delete` на `secret/metadata/...`, `update` на `secret/destroy/...` для `Prune` и `list` на
`secret/metadata/tenants/+/automation/secrets/` и его подпапки для `List`/подметания — без права читать значения)
и роль чтения (`read` на `secret/data/...` и `secret/metadata/...`). Без `list` подметание получит 403, примет его
за недоступность хранилища и не выполнится.
Сетевые сбои, 5xx, sealed/standby Vault - `ErrUnavailable`; 403 по токену процесса - тоже, не `ErrForbidden`
(последний - только для чужого арендатора). Префикс окружения задаётся `DefaultLocator("prod/")`.
