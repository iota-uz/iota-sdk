# Секреты автоматизаций: встроенный коннектор «Secret»

Секреты вида `API_KEY` арендатор ведёт на странице «Интеграции» как встроенный коннектор «Secret».
Запись секрета (имя, описание, ссылка на значение, версии, времена создания, ротации и последнего
использования) лежит в `automation.secrets`; **значение** лежит за портом хранилища
(`pkg/automation/secrets`). Страница и ноды видят только запись; значение после сохранения не показывается.

## Порт хранилища

```go
type Writer interface {
    Put(ctx context.Context, ref Ref, data map[string]string) (Metadata, error) // следующая версия значения
    Delete(ctx context.Context, ref Ref) error                                  // со всеми версиями; нет значения — не ошибка
    Prune(ctx context.Context, ref Ref, keepFrom int) error                     // удалить версии до keepFrom
    List(ctx context.Context, root Ref) ([]string, error)                       // пути со значениями под префиксом root.Path
}
type Reader interface {
    Read(ctx context.Context, ref Ref) (Value, error) // версия ref.Version (0 — последняя) целиком
}
type MetadataReader interface {
    Metadata(ctx context.Context, ref Ref) (Metadata, error) // версии и времена, не значение
}
type Store interface{ Writer; Reader; MetadataReader }
```

`Ref{TenantID, Path, Version}` - где лежит значение; `Version` выбирает версию для `Read` (0 - последняя). Путь формирует `Locator`; по умолчанию
`DefaultLocator(prefix)`: `<prefix>tenants/<tenant>/automation/secrets/<secret-id>` (prefix - окружение,
например `prod/`). Запись хранит `ref_path`, так что смена Locator не ломает уже созданные секреты.

Процесс может держать только `Writer` (управление) или только `Reader` (резолв в нодах): композиция
выдаёт каждому потребителю его часть.

### Контракт адаптера

- Значения версионируются как в KV v2: `Put` добавляет следующую версию, прежние остаются до `Prune`.
- `Read` возвращает одну версию целиком, никогда поля двух версий (у встроенного адаптера - одна строка и один запрос).
- `Put` виден следующему `Read` в любом процессе; кеша, переживающего ротацию, нет. Версия растёт атомарно.
- `Ref` без арендатора — `ErrForbidden`. Путь, который есть только у другого арендатора, для этого арендатора —
  `ErrNotFound`: адаптер не выдаёт, что путь существует где-то ещё, и значение не отдаёт.
- Недоступность хранилища, неподходящий ключ, повреждённая строка - `ErrUnavailable`. Вызывающий **никогда** не
  подменяет её переменной окружения или устаревшим значением.
- Ошибки не содержат значений.

## Встроенный адаптер

`connectors.NewSealedSecrets(db, keys)` хранит значение в `automation.secret_values`
(`tenant_id, path, version, key_id, nonce, ciphertext`, PK `(tenant_id, path, version)`): AES-256-GCM тем же кольцом
ключей, что и подключения; AAD связывает шифртекст с арендатором, путём и версией. Без кольца ключей
каждый вызов - `ErrUnavailable`, оборачивающий `connectors.ErrNotConfigured`. `Store.Rewrap` пере-шифровывает
значения секретов вместе с подключениями.

## Менеджер и резолвер

- `secrets.NewManager(db, writer, locator)`: `List`, `Create`, `Update` (имя, описание; с проверкой версии),
  `Rotate` (новая версия значения), `Delete` (значение и запись). Значение - не пустое, до 64 КиБ; имя -
  `^[A-Z][A-Z0-9_]{0,63}$`, уникально среди живых секретов арендатора (`ErrNameTaken`).
- **Протокол без удерживаемых соединений.** Ни один шаг не держит транзакцию (и соединение пула), пока
  пишется значение: хранилище может брать соединения из того же пула (встроенный адаптер так и делает), и
  пул из одного соединения иначе ждал бы сам себя. Состояние записи после любого сбоя говорит, что опубликовано:
  - *подготовлена*: `value_version = 0` - имя занято, никто её не читает, значение может быть или не быть;
  - *опубликована*: `value_version = N > 0` - читатели читают версию N;
  - *надгробие*: `deleted_at` - имя свободно, значение удаляется.
- **Заявка на запись.** Перед вызовом `Writer.Put` менеджер одним оператором отмечает запись
  (`value_write_at`). Надгробие хранится, а его значение удаляется заново при каждом `purge`, пока последняя
  заявка не старше окна записи (10 минут). Поэтому значение, записанное после удаления (ротация, которую обогнал
  `Delete`, или процесс, остановившийся сразу после записи), всегда находится по надгробию и удаляется.
- **Срок допуска записи.** `Ref.NotAfter` — момент, после которого адаптер не допускает запись (`ErrUnavailable`,
  ничего не записано); менеджер ставит его в заявку + половину окна (по часам БД). Встроенный адаптер проверяет
  его в самом вставляющем операторе. Это срок допуска, а не фиксации: допущенная раньше запись может
  зафиксироваться позже. Решение снять надгробие принимается **до** удаления значения: только если заявка тогда
  уже истекла и с тех пор не менялась. Срок лишь сужает окно гонки - гарантией не служит: хранилище может
  задержать уже начатую запись (оператор PostgreSQL, запрос к OpenBao, который клиент не может отменить).
- **Подметание (sweep) - гарантия.** Каждый `purge` перечисляет значения под корнем арендатора
  (`Locator.Root`, `Writer.List`) и удаляет те, что не названы ни живой, ни подготовленной записью. Сначала
  читается список хранилища, потом записи: создание вставляет подготовленную запись до записи значения,
  поэтому значение живого или создаваемого секрета не трогается. Запись, зафиксированная сколь угодно поздно
  (даже после удаления секрета и снятия надгробия), находится в списке хранилища и удаляется следующим
  подметанием: ссылка для очистки — само хранилище. Под корнем нельзя хранить ничего постороннего; пустой
  корень менеджер отвергает.
  **Смена корня (префикса Locator).** Уже созданные секреты читаются по сохранённому `ref_path`, но подметание
  видит только перечисленные корни. При смене префикса (например, `prod/` → `prod-v2/`) Locator композиции
  возвращает новый корень в `Root` (новые пути проверяются по нему) и реализует `secrets.FormerRoots`, отдавая
  старые корни: обычное подметание продолжает их перечислять тем же порядком (сначала список хранилища, затем
  записи, подготовленные записи сохраняются), поэтому поздняя запись под старым корнем всё равно удаляется.
  Отдельный разовый проход не нужен и гарантией не служит. `Rotate` пишет значение только под корнем, который
  подметается (текущим или из `FormerRoots`): запись, чей `ref_path` лежит вне всех корней (префикс сменили, а
  старый корень в `FormerRoots` не оставили), ротации получают `ErrUnavailable`, ничего не записывается —
  поздняя запись туда, где её никто не найдёт, невозможна; вернуть старый корень в `FormerRoots` достаточно,
  чтобы ротации снова работали. Убирать корень из `FormerRoots` можно только когда
  выполнены **оба** условия: (1) запись под ним больше не может зафиксироваться — ни поздняя запись удалённого
  секрета, ни ротация живого секрета, у которого `ref_path` лежит под старым корнем (такие секреты ротируются
  по своему пути, пока живы); (2) очистка подтвердила, что сирот там нет: последнее подметание старого корня
  завершилось без ошибок и в пределах пакета, а его список содержит только пути живых записей. Чистый список
  сам по себе не доказывает (1), а невозможность новых записей — не доказывает (2). Если хоть одно не
  установлено, держите корень всегда — это одно перечисление за очистку. Порядок перехода: (а) выкатить Locator
  с новым `Root` и старым корнем в `FormerRoots`; (б) дождаться, пока живых записей с `ref_path` под старым
  корнем не останется (секреты удалены или их значения перенесены вместе со ссылками) и пройдёт окно записи
  (10 минут) после последней заявки на запись под ним; (в) убедиться по условию (2) и только тогда убрать
  корень. Пока шаг (б) не выполнен, корень держится, иначе ротации таких секретов отказывают (см. выше).
- **Срок очистки.** `purge` (его запускают `List`, `Create`, `Rotate` и `Delete`) укладывается в один срок
  (`cleanupTimeout`, 5 секунд) целиком: половина — надгробиям, остальное — подметанию всех корней. Он не
  отвязан от вызывающего: отменённый запрос не ждёт очистки, недоделанное сделает следующий вызов. Корень, с
  которого начинается подметание, чередуется от очистки к очистке: медленный корень тратит не больше одной
  очистки и не мешает подметать остальные. Шаги после записи значения (сверка потерянного ответа, `Prune`,
  удаление значения удалённого секрета) отвязаны от отмены и делят один срок `cleanupTimeout` на вызов.
- **Срок записи.** Вызов `Writer.Put` получает контекст со сроком «заявка + половина окна» (считается от
  момента перед заявкой), поэтому зависшая запись бросается клиентом раньше, чем надгробие может быть снято;
  то, что хранилище всё же зафиксирует позже, убирает подметание.
- **`Put` возвращает свою версию**: ровно ту, что записал этот вызов, даже если параллельный `Put` уже добавил
  следующую; менеджер публикует только то, что записал сам.
- **Create**: вставить подготовленную запись → `Writer.Put` → опубликовать (`value_version = 1`). При ошибке
  менеджер перечитывает запись: опубликована (ответ на COMMIT потерян) - это успех, значение не трогается;
  подготовлена - одним оператором становится надгробием (опубликовать её уже нельзя, имя свободно), затем
  удаляется значение, а надгробие хранит ссылку, пока значение не удалено; записи нет - значение сирота и
  удаляется. Подготовленные записи старше 10 минут `purge` так же превращает в надгробия.
- **Rotate**: заявка на запись (запись должна быть живой) → `Writer.Put` (версия N+1) → одним оператором
  опубликовать с проверкой версии записи; из двух параллельных ротаций публикует одна, вторая получает
  `ErrVersionConflict`. Если запись за это время удалили, ротация сама удаляет записанное значение
  (а если не успела - его найдёт `purge`). Сбой между записями оставляет запись и читателей на N, а UI видит ошибку; потерянный ответ
  сверяется по записи. После публикации удаляются версии ниже ранее опубликованной N (`Prune(N)`): версия N
  остаётся для читателей, которые нашли запись перед ротацией; неопубликованная версия прерванной ротации
  между N и новой удаляется следующей успешной ротацией вместе с N.
- **Delete**: одним оператором надгробие (имя сразу перестаёт разрешаться и освобождается), затем значение и
  строка. Если хранилище недоступно, надгробие остаётся, и удаление повторяют следующие `List`, `Create`,
  `Rotate` и `Delete` арендатора (повторный `Delete` того же секрета тоже: он запускает очистку и возвращает
  `ErrNotFound`). `Update` очистку не запускает.
- `secrets.NewResolver(db, reader)`: `Has(ctx, tenant, name)` - только по записям, без чтения значения и
  отметки использования; `Resolve(ctx, tenant, name)` читает опубликованную версию (`value_version`). Если точной версии нет, резолвер
  перечитывает запись: ротация успела опубликовать новую и удалить старую - читает новую (до 3 попыток);
  запись не изменилась - `ErrUnavailable`. Нет
  записи - `ErrNotFound`; сбой записей или хранилища - `ErrUnavailable`. Значение читается при каждом вызове, поэтому ротация действует в
  работающем процессе без перезапуска. `last_used_at` обновляется не чаще раза в минуту и не может
  провалить чтение.

## Порядок разрешения имени в ноде

Нода (Code, HTTP) объявляет секреты по имени. `access.ChainSecrets` ищет:

1. секрет арендатора (коннектор «Secret»). Сначала `Has` по записям; если имя принадлежит арендатору, субъект,
   от имени которого идёт запуск, должен иметь `Secrets.Use` - иначе нода падает с кодом `secret_forbidden`,
   а значение не читается и использование не отмечается. Только после этого `Resolve`;
2. цепочка приложения (`access.FromResolver`): `CONNECTION__FIELD` - секретное поле подключения, затем
   `host.SecretResolver`. Поле с `"x-authorization-only": true` (токен и пароль коннектора HTTP/API) так не
   отдаётся никогда: им пользуется только авторизация самого подключения;
3. иначе код `secret_missing`, сообщение `unknown secret NAME`.

`ErrUnavailable` хранилища арендатора - управляемая ошибка `unavailable` (повторяемая); к цепочке приложения
в этом случае **не** переходим.

## RBAC

- `Secrets.Manage` - создавать, переименовывать, ротировать, удалять (набор прав `secrets_manage`);
- `Secrets.Use` - автоматизации пользователя читают секреты арендатора (набор `secrets_use`);
- `Connections.Use` - автоматизации пользователя вызывают подключения арендатора из Code и HTTP нод
  (`env.connections`, `auth: {connection}`): и HTTP-запросы, и Go-операции (набор `connections_use`). Без него
  нода получает `permission_denied` до обращения к провайдеру. Перед каждым вызовом статус подключения
  читается заново: выключенное или сломанное за время запуска подключение даёт `connection_disabled` /
  `connection_broken`, провайдер не вызывается.
- **Выдача прав после развёртывания.** Права создаются при старте/сиде, но в роли сами не попадают:
  только роль администратора, созданная сидом новой установки, получает все права. В существующей установке
  администратор открывает страницу «Роли», выбирает роль и включает наборы прав модуля «Automations»:
  «Управление секретами» (`secrets_manage` → `Secrets.Manage`) тем, кто ведёт секреты на странице
  «Интеграции»; «Использование секретов» (`secrets_use` → `Secrets.Use`) и «Использование подключений»
  (`connections_use` → `Connections.Use`) ролям, от имени которых работают автоматизации с Code и HTTP
  нодами. В стандартные роли эти права не добавляются: доступ к секретам и подключениям — явное решение.
- **Без ключа шифрования.** Встроенное хранилище без кольца ключей отвечает `ErrUnavailable` на любой вызов
  (`secrets.Configurable`: `Configured() == false`). Страница тогда показывает список, но не предлагает
  «Добавить секрет» и ротацию (`secrets_configured: false` в `automations.connectors.list`) и объясняет почему.
  Адаптер, который всегда может писать (OpenBao), `Configurable` не реализует.
- **Обновление.** До этого изменения в SDK не было ни одного `CodeAccessor`, поэтому Code и HTTP ноды на
  встроенных коннекторах подключениями не пользовались. Приложение, которое само зарегистрировало коннектор с
  `CodeAccessor` (`automations.WithConnectors`), должно при обновлении выдать `Connections.Use` (набор
  `connections_use`) ролям, от имени которых работают его автоматизации; иначе такие ноды получат
  `permission_denied`.

## Заменить адаптер

```go
composition.Provide[secrets.Store](b, func(c *composition.Container) (secrets.Store, error) {
    return myopenbao.New(...), nil // Writer + Reader + MetadataReader
})
```

Менеджер, резолвер и Locator собираются поверх `secrets.Store`, записи остаются в PostgreSQL.

**Так можно поставить новую установку.** Замена адаптера значения не переносит: запись в PostgreSQL ссылается на
путь и версию (`ref_path`, `value_version`), и если у нового адаптера их нет, `Resolve` вернёт `ErrUnavailable`.
Для установки с секретами нужен согласованный переход: либо перенести каждое значение так, чтобы новый адаптер
отдавал его по тому же пути и той же опубликованной версии, либо переносить значения и обновлять ссылки в
записях вместе (в окне, когда управление секретами закрыто), и только потом переключать композицию.

## Следующий шаг: адаптер OpenBao KV v2 (#1382)

| Порт | KV v2 (mount `secret`) |
| --- | --- |
| `Put(ref, data)` | `POST /v1/secret/data/<ref.Path>`, тело `{"data": {...}, "options": {"cas": <current_version>}}`: `current_version` читается из `GET /v1/secret/metadata/<ref.Path>` (0, если пути нет); при конфликте CAS — перечитать и повторить, ограниченное число раз (как встроенный адаптер — 8), затем `ErrUnavailable`. Версия из ответа — `Metadata.Version`. `ref.NotAfter`: не отправлять запрос после срока (запоздавшую запись, которую уже не отменить, уберёт подметание). Хранение версий — см. ниже «Хранение версий в KV v2» |
| `List(root)` | `LIST /v1/secret/metadata/<root.Path>` (рекурсивно по подпапкам) |
| `Read(ref)` | `GET /v1/secret/data/<ref.Path>?version=<ref.Version>` (без параметра при 0) - версия целиком (`data.data`, `data.metadata.version`); 404 - `ErrNotFound` |
| `Metadata(ref)` | `GET /v1/secret/metadata/<ref.Path>` - `current_version`, `created_time`, `updated_time` |
| `Delete(ref)` | `DELETE /v1/secret/metadata/<ref.Path>` - все версии; 404 не ошибка |
| `Prune(ref, keepFrom)` | `POST /v1/secret/destroy/<ref.Path>` с `{"versions": [1..keepFrom-1]}` |

### Хранение версий в KV v2

Опубликованная версия (и предыдущая, которую `Prune` оставляет читателям) не должна пропасть ни от вытеснения,
ни от истечения, в том числе при сбоях публикации и параллельных записях.

- **Вытеснение.** KV v2 держит не больше `max_versions` версий (`0` или не задано — значение по умолчанию, 10,
  а не «без предела») и при записи сверх предела удаляет самую старую. `destroy` (наш `Prune`) помечает версии
  уничтоженными, но `oldest_version` не сдвигает, поэтому считать от `oldest_version` нельзя. Адаптер в том же
  чтении `GET /v1/secret/metadata/<path>`, что даёт `current_version` для CAS, берёт из `versions` самую старую
  **не уничтоженную** версию `oldest_live` и отказывает (`ErrUnavailable`, ничего не записано), если запись
  вытеснила бы её: `current_version + 1 − oldest_live + 1 > max_versions`. Вытесняются тогда только уже
  уничтоженные версии, что безвредно. После 100 и более успешных ротаций `oldest_live` — это предыдущая
  опубликованная версия, и проверка проходит; около предела её заполняют только подряд идущие неопубликованные
  записи (сбои публикации) — тогда ротация отказывает, пока публикация или `Prune` не освободят место, а
  опубликованная версия остаётся читаемой. CAS делает проверку и запись одним шагом и для параллельных записей.
  Предел — явный `max_versions = 100` в метаданных пути (адаптер ставит его при первой записи пути).
- **Истечение.** Действует наименьшая ненулевая из `delete_version_after` mount и пути, поэтому `0` на пути не
  отключает срок mount. Нужно `delete_version_after = 0` **и** в конфигурации mount (`secret/config`), **и** в
  метаданных пути (адаптер ставит при первой записи).
- **Защита настроек.** CAS не защищает настройки хранения. `secret/config` mount не может менять ни одна из
  ролей приложения (только оператор); настройки метаданных пути (`max_versions`, `delete_version_after`) пишет
  только адаптер под ролью записи при создании пути, роль чтения их менять не может. Кроме того, адаптер перед
  каждой записью сверяет их по тому же чтению метаданных пути, а `delete_version_after` mount — по
  `GET secret/config` (при старте и периодически); при расхождении он отказывает в записи (`ErrUnavailable`)
  вместо того, чтобы писать в хранилище, которое может удалить опубликованную версию.

Политики разделены. В OpenBao `*` допустим только в конце пути, `+` — один сегмент; если в `ref.Path` есть
префикс окружения (`DefaultLocator("prod/")`), он входит в путь политики:

```hcl
# роль записи (управление секретами): без права читать значения
path "secret/data/prod/tenants/+/automation/secrets/*"     { capabilities = ["create", "update"] }
path "secret/metadata/prod/tenants/+/automation/secrets/*" { capabilities = ["create", "update", "read", "list", "delete"] } # настройки пути при создании, current_version/versions для CAS и проверки, List, Delete
path "secret/config"                                       { capabilities = ["read"] }                   # сверка delete_version_after mount
path "secret/metadata/prod/tenants/+/automation/secrets/"  { capabilities = ["list"] }                   # корень для List/подметания
path "secret/destroy/prod/tenants/+/automation/secrets/*"  { capabilities = ["update"] }                 # Prune

# роль чтения (резолв в нодах)
path "secret/data/prod/tenants/+/automation/secrets/*"     { capabilities = ["read"] }
```

`read` на `secret/metadata/...` отдаёт версии и времена, но не значения (они только в `secret/data/...`). Для роли
одного арендатора вместо `+` пишется его id. Без `list` подметание получит 403, примет его за недоступность
хранилища и не выполнится.
Сетевые сбои, 5xx, sealed/standby Vault - `ErrUnavailable`; 403 по токену процесса - тоже, не `ErrForbidden`
(последний - только для чужого арендатора). Префикс окружения задаётся `DefaultLocator("prod/")`.
