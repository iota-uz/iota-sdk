# Коннектор Telegram bot (`telegram_bot`)

`pkg/automation/connectors/telegram` — коннектор графов автоматизаций (#1341): отправка сообщения,
вопрос с кнопками, ожидание текстового ответа и триггер на входящее сообщение боту. Клиент —
`gotgbot/v2`; токен бота никогда не попадает в output, логи и ошибки (URL Bot API содержит токен, поэтому
ни одна ошибка запроса его не несёт).

## Подключение в приложении

Модуль `automations` регистрирует коннектор сам (как OpenAI, SMS и MCP), если приложение не зарегистрировало
свой коннектор `telegram_bot` через `WithConnectors`; `automations.WithoutTelegram()` его убирает. Модуль собирает:

| Поле `telegram.Config` | Откуда |
| --- | --- |
| `PlatformToken` | `APP_TELEGRAMBOTTOKEN` (запись `telegram_bot` в `AUTOMATION_PLATFORM_CREDENTIALS` имеет приоритет); пусто — платформенного бота нет |
| `PublicOrigin` | origin приложения (`httpconfig.Origin`), на него указывают webhook-и |
| `Inbound` | `engine.Runtime.Inbound()` модуля |
| `Uploads` | `uploads.NewTelegramUploads(uploadService, pool, uploadsCfg.PrivatePath())`, если в композиции есть сервис загрузок ядра |
| `Connections`, `Usage` | хранилище подключений модуля и `automation.connector_usage` |

Свой коннектор (например, с `RegisterStart`) приложение регистрирует так:

```go
tg := telegram.New(telegram.Config{
    PlatformToken: cfg.App.TelegramBotToken,
    PublicOrigin:  origin,
    Inbound:       runtime.Inbound(),
    Uploads:       uploads.NewTelegramUploads(uploadService, pool, uploadsCfg.PrivatePath()),
    Connections:   store,
})
_ = tg.RegisterStart(userLinking) // необязательно: StartHandler (#1349)
automations.NewComponent(automations.WithConnectors(tg))
```

Поле `chat_id` нод выбирается в редакторе из чатов подключения: хост редактора (`presentation/graphs`) реализует
`EditorApi.searchOptions` методом RPC `automations.search_options` (`source`, `query`, `connection`; право
`Automations.Author`), который спрашивает `connectors.OptionSource` коннектора подключения. Шаг без подключения
берёт единственное подключение своего вида, платформенный credential вариантов не даёт.

- Креды: `token` (x-secret). Webhook secret генерирует коннектор при `Provision` (32 символа
  `[A-Za-z0-9_-]`) и отдаёт сервису, тот пишет его в inbound state подключения (ключ `telegram_webhook`) в
  той же транзакции, что и сохранение; `Verify` читает его оттуда (`connectors.InboundReader`). У бота платформы
  строки подключения нет, его секрет выводится HMAC-ом из токена (`WebhookSecret`).
- Сохранение подключения вызывает `setWebhook` на `/automations/hooks/{connection_id}`; удаление и
  отключение — `deleteWebhook` (только если webhook ещё наш; ошибка вызова не мешает удалению). Это
  `connectors.Provisioner`, его вызывает `IntegrationsService`. Бот платформы регистрируется при старте
  модуля `automations` (`connectors.PlatformStarter`) на `/automations/hooks/platform/telegram_bot`.
- Бот платформы (политика `auto`) доступен всем тенантам как платформенный credential. Его входящие
  апдейты не публикуются, кроме нажатия кнопки (тенант — по токену корреляции) и `/start <payload>` с
  зарегистрированным префиксом (`StartHandler.TenantOf`). Поэтому триггер «входящее сообщение»
  работает только для собственного бота тенанта.

## Один бот — одно подключение

У бота один webhook, поэтому бот не может принадлежать двум подключениям, включая бота платформы. Владение
фиксируется в БД (`automation.exclusive_identities`, `connectors.ExclusiveIdentity`): id бота резервируется за
подключением (или за платформенным credential при старте модуля) в транзакции сохранения под advisory-lock на
этот id, поэтому два одновременных сохранения не могут оба настроить webhook; проигравшее получает ошибку поля
`token` (`in_use`), подтверждение её не снимает. Резерв держит и отключённое подключение, снимает удаление.
Для старых подключений без резерва остаётся проверка `getWebhookInfo`: webhook этого приложения на живое
другое подключение (`ConnectionExists`) или на маршрут бота платформы — тоже `bot_in_use`; webhook удалённого
подключения ничей. `Deprovision` удаляет webhook только при точном совпадении URL.
Платформенный бот регистрируется и резервируется для credential, который действует (конфигурация имеет
приоритет над `APP_TELEGRAMBOTTOKEN`): `StartPlatform(ctx, creds)`.

## Чужой webhook

Перед сохранением и перед повторным включением отключённого подключения `Advise` (`connectors.Advisor`) читает `getWebhookInfo`; если у бота webhook на чужой
URL (`foreign_webhook`) или webhook нет вовсе (`polling_unknown`: опрашивает ли бота другой сервис, узнать нельзя —
запрос `getUpdates` перехватил бы долгий опрос), форма
показывает предупреждение и не завершает подключение без подтверждения (`confirm` в
`create`/`update`/`set_disabled`, ошибка `confirmation_required`). `Test` при этом проходит.

`Provision` авторитетен: он заново смотрит webhook в момент изменения и сам требует подтверждение (`consent`), а
`Advise`, не сумевший получить состояние провайдера, отказывает в сохранении. Секрет подключения привязан к аккаунту бота и сохраняется между
сохранениями и повторными включениями того же бота (при смене бота генерируется новый), `Provision` читает inbound state
из транзакции сохранения (одно соединение с БД), поэтому не завершившееся сохранение или
конкурирующее не оставляет Telegram с секретом, которого нет в SDK; такое сохранение снимает webhook, который успело
поставить. Повторное включение — одна транзакция за проверкой версии строки. Очистка webhook (отключение, замена токена, неудачное
сохранение) выполняется под тем же advisory-lock на аккаунт и по свежему состоянию строки (`Store.WithLatest`): запоздавшее
отключение не удалит webhook успешного включения. Резерв аккаунта следует за кредами при любом статусе (в том числе у
отключённого подключения). Платформенный credential, чей аккаунт занят подключением тенанта, снимается с выдачи
(`PlatformWithdrawer`); при удалении настройки платформенного бота его резерв освобождается (webhook без токена не
снять). Если платформенный credential занят, а `PlatformWithdrawer` недоступен, приложение не стартует с ним. Маршрут
`/hooks/platform/telegram_bot` занят только текущим платформенным ботом: бот, бывший платформенным до ротации, свободен для
подключения тенантом (его старый webhook на этом маршруте уже никто не обслуживает). Резерв платформенного бота — lease (`connectors.PlatformLease`,
2 минуты, колонка `lease_until`): каждый экземпляр, работающий с платформенным credential, продлевает его каждые 30 секунд, а
резерв, который никто не продлил дольше lease, снимается (`PrunePlatformIdentities`, при старте и при продлении). Поэтому при
выкатке (rolling), меняющей платформенного бота, старые экземпляры держат резерв прежнего бота, пока работают: тенант не может
подключить его и поставить webhook, а старт нового экземпляра не снимает резерв из-под старых (и старт старого — резерв нового).
Прежний бот освобождается через lease после остановки последнего старого экземпляра. Старт платформенного бота (резерв и
`setWebhook`) выполняется под той же advisory-lock на аккаунт, что и сохранение подключения: два экземпляра, стартующие с одним
ботом, ставят webhook по очереди, а сохранение тенанта ждёт и видит резерв. Если lease истёк (база была недоступна) и аккаунт
занял тенант, продление снимает платформенный credential с выдачи; поэтому набор `connectors.PlatformCredentials` без
`PlatformWithdrawer` с платформенным ботом не стартует (`automations.ErrPlatformNotWithdrawable`). Сбой самой проверки
резерва (ошибка базы) credential не снимает: webhook не ставится, бот продолжает отправлять, продление резервирует его,
когда база ответит. Lease отсчитывается от момента, когда `setWebhook` вернулся (`clock_timestamp()`), а строка резерва
заблокирована до конца транзакции, так что очистка истёкших резервов не удалит её во время продления. Резерв коммитится
до вызова `setWebhook`, а сам вызов ограничен `connectors.PlatformStartTimeout` (половина lease) и так, чтобы к его дедлайну
оставалась четверть закоммиченного lease (ожидание блокировки идёт в счёт; если времени меньше, установка не выполняется):
если сессия базы оборвётся во время запроса к Telegram, аккаунт остаётся зарезервирован. У Telegram нет условного
`setWebhook`, поэтому запрос, который Telegram применит позже чем через четверть lease после дедлайна клиента (от
упавшего экземпляра: живой продлевает lease каждые 30 с), может направить бота, которого уже занял тенант, обратно на
маршрут платформы. Это восстанавливается само: при удалении платформенного резерва аккаунт записывается в
`automation.retired_platform_identities` (без срока: тенант может подключить бота когда угодно позже), и апдейт на маршруте платформы, который текущий платформенный credential не
проверяет, ищется по индексу: хеш секретного заголовка (`connectors.StrayKeyOf`) сохраняется с резервом платформы при старте
и переходит в запись о выведении, поэтому запрос без заголовка отклоняется сразу, а с заголовком находит не больше одного
аккаунта; только его учётные данные читаются, и секрет сверяется с платформенным секретом его токена
(`engine.PlatformStrayReceiver`). Совпавший бот получает обратно webhook своего подключения с его секретом (секрет читается до блокировки,
а под блокировкой аккаунта webhook ставится, только если версия подключения не изменилась: работает и на пуле из одного
соединения), а запрос — 503: следующую доставку Telegram отправит уже подключению
(`TestTelegramStrayPlatformWebhookIsPointedBackToItsConnection`).

### Первое обновление до этой версии (обязательно)

Касается приложений, где уже настроен платформенный бот (`APP_TELEGRAMBOTTOKEN` или запись `telegram_bot` в
`AUTOMATION_PLATFORM_CREDENTIALS`), то есть приложений на SDK до этой версии (например v0.55.x), которые подключили коннектор
сами. Без платформенного бота процедура не нужна.

Предыдущая версия ставит webhook платформенного бота при старте вне какой-либо блокировки и при перезапуске ничего не пишет
в базу. Поэтому её `setWebhook` нельзя ни сериализовать с новой версией, ни обнаружить. Первое обновление должно идти
**без перекрытия версий**:

1. Остановите все экземпляры предыдущей версии: Railway — реплики в 0, Kubernetes — стратегия `Recreate`, docker compose —
   `down`, затем `up`. Выкатка rolling с одновременно работающими старыми и новыми экземплярами для этого перехода не допускается.
2. Запустите экземпляры этой версии. Платформенный токен и origin в этой же выкатке не меняйте: тогда новый старт видит
   webhook бота на своём же маршруте (`hookOwn`) и ставит его заново под блокировкой аккаунта.
3. Проверьте: `curl -s "https://api.telegram.org/bot$APP_TELEGRAMBOTTOKEN/getWebhookInfo"` возвращает
   `url = <origin>/automations/hooks/platform/telegram_bot`, а `last_error_message` после первого апдейта пуст.

Дальнейшие выкатки этой версии и новее могут идти rolling: старт и установка webhook сериализуются блокировкой аккаунта, а
резерв держится lease (см. выше).

### Смена origin при том же платформенном боте

Старт не перехватывает webhook, который указывает на другой адрес: URL прежнего origin для него чужой (`hookForeign`), и
webhook на новом адресе сам не появится. Перенос делается явно, отдельной выкаткой:

1. Перед выкаткой снимите webhook, не теряя ожидающие апдейты (Telegram хранит их до 24 часов):
   `curl -s "https://api.telegram.org/bot$APP_TELEGRAMBOTTOKEN/deleteWebhook?drop_pending_updates=false"`.
2. Выкатите приложение с новым origin. Старт видит бота без webhook (`hookFree`) и ставит
   `<новый origin>/automations/hooks/platform/telegram_bot` со своим секретом.
3. Проверьте через `getWebhookInfo`: `url` — новый адрес, а `pending_update_count` уменьшается до 0 по мере доставки.
   Если `url` пуст, старт не смог поставить webhook (в логе приложения есть предупреждение
   `the platform credential of telegram_bot was not set up`). Тогда перезапустите приложение или включите
   `telegram.Config.ReplacePlatformWebhook` у своего коннектора.

Webhook-и подключений тенантов при смене origin тоже переносятся явно: на экране интеграций каждое подключение Telegram
нужно «Отключить» и снова «Включить». Повторное включение вызывает `Provision`, тот видит webhook прежнего origin как чужой
(`foreign_webhook`), просит подтвердить и после подтверждения ставит URL нового origin. Либо до выкатки снимите их webhook
так же через `deleteWebhook` с токеном бота. Тогда предупреждения не будет.

### Смена платформенного токена

Смена бота — отдельная выкатка после первого обновления. Новый бот должен быть без webhook или с webhook этого приложения.
Rolling допустим: экземпляры с прежним ботом держат его резерв, пока работают (lease). Прежний бот после этого выводится
(см. ниже), его webhook снять без его токена приложение не может: снимите его сами через `deleteWebhook` с прежним токеном
или оставьте, если бота подключит тенант.

Что база гарантирует сама: резерв с действующим lease не удалит никто (триггер `keep_live_platform_leases`;
`ReleasePlatformIdentities` — явное снятие оператором — проходит), поэтому старый экземпляр не снимет резерв нового бота
(`TestThePreviousReleaseCannotReleaseALiveLease`, операторы прошлой версии дословно). Строка, записанная старым экземпляром,
держится 10 минут без продления; при том же токене её продлевают новые экземпляры.

Выведенный бот (бывший платформенный после смены токена) отклоняется маршрутом платформы: его секрет выводится из токена,
которого у приложения больше нет, поэтому аутентифицировать его апдейты нельзя — 404, ничего не публикуется. Нажатие кнопки
вопроса, заданного прежним ботом, до ответа не доходит, вопрос ждёт своего таймаута (`TestTelegramRetiredPlatformBotIsRefused`).
Во время выкатки нажатие кнопки прежнего бота, попавшее на новый экземпляр, отклоняется так же. Повторное включение и замена токена на
бота без webhook требуют подтверждения `polling_unknown`.

## Ноды

| Нода | Поведение | Outcomes |
| --- | --- | --- |
| `telegram.send` | call, не идемпотентна | `sent`, `failed` |
| `telegram.ask` | call + ожидание нажатия | `<options[].outcome>`, `timeout`, `failed` |
| `telegram.read` | wait на `telegram.message_received.v1` | `received`, `timeout` |

- `chat_id` — число (id чата) или выражение CEL (`event.chatId`); для `telegram.send` и `telegram.ask` ещё `"@username"`.
  `telegram.read` ждёт в чате по числовому id (или выражению, которое его даёт): `"@username"` там отклоняется при проверке
  графа. `thread_id` — тема форума.
  В редакторе поле выбирается из известных чатов («Личные», «Группы»), вводится вручную (id или
  @username) или задаётся выражением (`x-options-source: telegram.chats`, `EditorApi.searchOptions`).
- `send.files` — id загрузок: один файл идёт как фото/документ с подписью, несколько — альбомом документов.
- `ask`: кнопка — `callback_data = a:<токен корреляции>:<номер>` (≤ 64 байт), таблицы соответствий нет.
  Каждое нажатие подтверждается `answerCallbackQuery`; после первого принятого ответа (после коммита, см.
  `engine.PublishedAnswerer`) клавиатура снимается, а текст дополняется `→ <выбранный вариант>`. Нажатие
  закрытого или просроченного вопроса получает «Ответ уже принят или время истекло» и снимает клавиатуру;
  при самом таймауте сообщение не меняется. Outcome по номеру кнопки определяет `engine.ParamAnswerer`.
- `read` работает только с собственным ботом тенанта (платформенный credential не предлагается и не принимается,
  `catalog.TenantConnectionNode`); если беседу назвать нельзя (чат по @username, подключение не определилось), нода
  падает, а не слушает беседу запуска. Ждёт только сообщение с текстом (вложение без подписи — событие для триггеров, но не ответ); подключение,
  если оно не указано, движок определяет как для вызова и строит conversation `<connection_id>:<chat_id>`
  из отрендеренного `chat_id`. `from_user_id` — id или выражение, читаемое в момент прихода сообщения (`nodes.<id>.output…`;
  `event` там — входящее сообщение, поэтому выражение с `event` отклоняется). Output — `{event: <payload>}`.
- Шаблоны внутри списков (`options[].label`, `url_buttons[].text`) — путь `items[].field` в
  `NodeSpec.Templates`/`Values`.

## События

`telegram.message_received.v1` (conversation `<connection_id>:<chat_id>`; только собственные боты тенанта — для
этого события каталог не предлагает и не принимает платформенный credential (`catalog.TenantConnectionTriggers`);
свои сообщения бота — `by_self`; сообщение без текста, но с файлом тоже событие, `event.text` пуст;
`files[]` — `upload_id, name, mime, size, url` или `error`: `too_large` (>20 МБ), `download_failed`,
`storage_failed`, `no_storage`). Параметры триггера: `commands: ignore|only|include` (по умолчанию
`ignore`), `command_names`, `chat_ids`, `private_only`. `/start` с префиксом `StartHandler` не публикуется.
`chat_ids` приводятся к каноническому десятичному виду при разборе (`"00042"` — это `"42"`); ключ дедупликации события — «id
бота:update_id» (update_id у Telegram свой у каждого бота: бот, заменивший прежний за тем же подключением, не принимается за повтор;
новый токен того же бота — тот же ключ). Файлы повторной доставки того же апдейта берутся из памяти процесса (15 минут), а не
сохраняются заново; повтор после этого срока или на другой реплике оставляет копию без ссылки из события.

Платформенный бот при старте приложения не перехватывает чужой webhook: если у бота уже есть webhook другого сервиса (или другого
подключения), `StartPlatform` возвращает ошибку, приложение стартует, а платформенный бот только отправляет сообщения. Платформенному
токену нужен бот «для себя»; для осознанного перехвата — `Config.ReplacePlatformWebhook`. Если база недоступна и резерв аккаунта
проверить нельзя, webhook платформенного бота при старте тоже не ставится.

`telegram.read` ждёт в чате по числовому id: чат по `@username` отклоняется при проверке графа (диалог не имеет ключа, пока
username не разрешён в id). Ссылка на `event` в `from_user_id` определяется по разбору CEL, а не по слову в строке. Если провайдер
отказывается убрать webhook после несохранённого сохранения, это записывается в лог сервиса (`Logger` в `IntegrationsDeps`).
Отключение подключения снимает webhook, только если он принадлежит этому подключению, но у Telegram нет «удалить, если URL равен»:
между чтением и удалением чужой webhook, поставленный независимым писателем, будет снят; такое возможно только для бота,
которым управляют несколько сервисов, а бот подключения предполагается под единоличным управлением SDK.

`StartUpdate.UpdateKey` — ключ апдейта («id бота:update_id»), одинаковый при каждой доставке. Обработчик, который тратит
одноразовую ссылку, хранит результат под этим ключом в той же транзакции и возвращает его при повторном вызове: тогда повторная
доставка после потерянного результата отправит первый ответ, а не «ссылка неизвестна или использована». Обработчик, реализующий `StartTenantByKey` (`TenantOfUpdate(ctx, updateKey)`), ещё и сообщает, чей это был апдейт: так ответ платформенного бота при такой повторной доставке засчитывается тому же тенанту.

`Uploads` — адаптер хоста: `NewTelegramUploads` хранит вложения чатов приватно, как вложения Email (#1439): файл —
загрузка тенанта в приватном пространстве `.private/automations-telegram/<tenant>` (`services.TelegramAttachmentsNamespace`),
публичный файловый обработчик и маршрут `/uploads/<id>` ядра его не отдают. `files[].url` — маршрут модуля
`/automations/attachments/<id>`: он требует вход, отдаёт файл только пользователю того же тенанта с правом
`Automations.Read` и всегда как скачивание (`Content-Disposition: attachment`, `sandbox`, `nosniff`; HTML, SVG и скрипты
идут как `application/octet-stream`). Файл, полученный дважды, — одна загрузка; если у тенанта уже есть публичная загрузка
или вложение письма с тем же содержимым, вложение — она (маршрут её тоже отдаёт); содержимое чужого приватного пространства
не сохраняется (`files[].error: storage_failed`). `Open` для `telegram.send` читает только то, что отдаёт маршрут вложений
(публичные загрузки тенанта и полученные коннекторами файлы), а не приватные файлы других функций; файлы, сохранённые до этого
изменения под суффиксом `.tg.txt`, открываются под исходным именем.
Коннектор проверяет тенанта в `Open` для исходящих отправок.

Подтверждение предупреждения (`confirm`) привязано к аккаунту: токен предупреждения — `код@id бота` (`foreign_webhook@222222`).
Подтверждение, данное для одного бота, не принимается для другого после смены кредов: сервер спросит снова. Экран показывает
фразу кода, а при повторных `confirmation_required` отправляет все уже подтверждённые токены вместе с новым.

`/start <payload>` обрабатывается коннектором сам и сохраняется в `automation.inbound_actions`
(`connectors.InboundActions`) по ключу «маршрут@id бота, событие, update_id» (update_id у Telegram свой у каждого бота, а маршрут
платформы или подключения остаётся при смене бота). Состояния: `claimed` → `handled` → `delivering` → `done`. Обработчик и
отправка ответа захватываются атомарно по отдельности: две доставки не запустят обработчик дважды, а повторная доставка,
пришедшая во время отправки ответа первым запросом, получает 503 и не отправляет ответ ещё раз. Результат обработчика (ответ)
хранится отдельно от отправки: если ответ не ушёл (429, 5xx, обрыв), захват отправки отдаётся, webhook отвечает 503, и повторная
доставка шлёт сохранённый ответ, не вызывая обработчик (одноразовая ссылка уже потрачена). Если результат отправки неизвестен
(5xx, обрыв), ответ может уйти дважды — это предпочтительнее потерянного ответа. Окончательный отказ (чат заблокировал бота)
завершает апдейт. Каждый захват несёт токен владельца: захват, не завершённый за 2 минуты, берётся заново с новым токеном, а
запись прежнего владельца отклоняется (`ErrInboundLost`, ответ 503) и не затирает работу преемника; обработчик и отправка
ограничены 60 секундами: это запрос на отмену контекста, а не остановка кода. Обработчик `StartHandler` обязан учитывать
отмену контекста; токен владельца защищает только запись в таблицу действий, а побочные эффекты обработчика, не
прервавшегося по отмене, не откатываются.
Если очистка клавиатуры на позднем нажатии не удалась, webhook тоже отвечает 503.

`telegram.callback_answered.v1` — нажатие кнопки; только будит `ask`.

## Ошибки и лимиты

- `403` и `400 chat not found` и подобные — `failed`, код `rejected`; соединение остаётся `connected`.
- `401` — `failed` с кодом `unauthorized`, соединение получает `needs_reauth`.
- `429` — `CallResult.RetryAfter` из `retry_after`; повтор по правилу движка, второго сообщения нет.
- Потерянный ответ после отправки — `outcome_unknown`, а не повтор.
- Каждое доставленное сообщение (альбом файлов — несколько) пишется в `UsageRecorder` (`unit: message`), для
  платформы и тенанта раздельно; ответ на `/start` считается тому тенанту, чья ссылка (`Config.Usage`).
- Альбом из нескольких файлов не принимает url-кнопки (проверка при сохранении графа и перед отправкой).
