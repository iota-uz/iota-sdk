## Контекст

Отдельные `UserFormOptionsRepository` и `UserFormOptionsService` решали проблему
полноты списков, но называли переиспользуемые read-модели по конкретному экрану
и дублировали существующий query-слой. Одновременно списки пользователей и групп
гидратировали связи запросами на каждую строку, а страница пользователя
загружала полные группы только ради их названий.

## Решение

Лёгкие tenant-scoped проекции назначения добавляются в существующие
`RoleQueryRepository` и `GroupQueryRepository`. Они возвращают все варианты в
детерминированном порядке вместе с эффективными разрешениями для RBAC-проверки,
не имеют скрытой пагинации и не загружают агрегаты или участников групп.
Списочные методы групп и пользователей сохраняют подробные контракты, но
гидратируют связи пакетно с фиксированным числом запросов. Для подписей групп
используется отдельная лёгкая выборка по ID.

Presentation builder координирует существующие query-сервисы, применяет общую
чистую policy grantability и формирует свойства формы. В edit текущие назначения
остаются видимыми, даже если оператор больше не вправе выдавать их. Командные
проверки продолжают работать с блокировками и полными доменными агрегатами.

## Последствия

Read-модели именуются по назначению данных, а не по форме. Непагинированный
список соответствует UI combobox; будущий удалённый поиск потребует явного
контракта поиска и изменения компонента, а не скрытого лимита. Проекция
пользователя включает прямые, ролевые и унаследованные через группы разрешения,
чтобы проверка доминирования оставалась fail-closed.

## Проверка

Интеграционные тесты проверяют обязательный tenant до SQL, полный список больше
стандартной страницы, group-inherited permissions и постоянное число запросов
для вариантов и пакетной гидратации. Browser E2E проверяет create, edit и
повторный рендер после ошибки валидации.
