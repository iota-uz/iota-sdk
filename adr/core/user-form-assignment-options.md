## Контекст

Формы создания и редактирования пользователя собирали варианты назначения из
разных источников. Роли загружались как доменные агрегаты, а группы — через
постраничный query-репозиторий с искусственным большим лимитом и полной загрузкой
участников. Контроллер самостоятельно объединял загрузку и RBAC-фильтрацию.
Из-за этого количество SQL-запросов зависело от размера групп, список мог быть
неполным, а уже назначенные значения исчезали после изменения прав оператора.

## Решение

Для пользовательских форм вводится отдельный tenant-scoped read contract. Он
возвращает все роли и группы в детерминированном порядке как лёгкие проекции с
эффективными разрешениями, необходимыми для RBAC-проверки. Контракт не имеет
пагинации и не загружает пользователей или доменные агрегаты; его число запросов
постоянно относительно количества вариантов и участников групп.

Единый сервис вариантов формы применяет политику grantability и формирует данные
для create, edit и повторного показа после ошибки валидации. В edit к доступным
вариантам добавляются текущие назначения пользователя, даже если оператор больше
не вправе выдавать их. Остальные недоступные варианты скрываются. Доменные
репозитории остаются источником полных агрегатов для команд и бизнес-операций.

## Последствия

Новые поля выбора добавляются в один read model и один builder, а контроллеры не
координируют репозитории. Непагинированный список намеренно соответствует UI
combobox; если количество ролей или групп потребует удалённого поиска, контракт
и компонент должны быть заменены вместе, а не скрытым лимитом. Уже назначенное,
но недоступное значение видно в edit; серверная policy остаётся окончательной
проверкой любой отправленной команды.

## Проверка

Интеграционный тест проверяет tenant isolation, полный список больше стандартной
страницы, порядок и фиксированное число SQL-запросов. Сервисный тест покрывает
RBAC-фильтрацию и сохранение текущих назначений. Browser E2E проверяет create,
edit и повторный рендер после ошибки валидации.
