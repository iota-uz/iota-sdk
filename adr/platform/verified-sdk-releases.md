## Контекст

Частые итерации агентов повторно запускают дорогие integration и E2E проверки
на PR и после merge. Ручные метки и отдельные команды публикации легко забыть.
Публичный Go-тег уже делает версию доступной, поэтому проверять её после тега поздно.

## Решение

На PR выполняются проверки без сервисов на стандартных GitHub runners. Полный
suite выполняется на неизменяемом кандидате по запросу потребителя до создания
тега. Go и npm имеют одну SemVer-версию и SHA исходников. Production-потребитель
ждёт завершения обеих публикаций. Preview остаётся локальным и временным.

CLI расширяет существующий Go sdk-tools. GitHub Actions хранит очередь в отдельной
ветке состояния с optimistic concurrency и продолжает работу независимо от агента.
Приватные сведения о потребителях остаются в их репозиториях. Частичная публикация
возобновляется с тем же архивом и SHA. Непрошедшие тесты не повторяются автоматически
на неизменившемся исходном commit.

## Обоснование

Намерение использовать изменение автоматически запускает выпуск. Несколько PR
оплачивают один полный прогон, а движение main не отменяет уже проверяемый batch.
Разделение принятого изменения и проверенного релиза сохраняет быстрый поток PR.

## Отклонённые альтернативы

- Полный CI на каждом PR и push: повторная стоимость промежуточных итераций.
- Ручная метка перед каждым релизом: корректность зависит от памяти агента.
- Проверки после push тега: Go-версия доступна до завершения проверки.
- Отдельный постоянно работающий сервис: дополнительная инфраструктура для
  процесса, состояние которого уже можно хранить в GitHub.

## Последствия

main может содержать интеграционный дефект до следующего кандидата. Потребители
должны подключить общий workflow и отказаться от production SHA-finalizer.
GitHub App и защита тегов требуют настройки. В v0 breaking change повышает minor;
переход к v1 и новая major-версия Go требуют отдельного решения.

## Как проверить

В .claude/tools выполнить `go test -race ./...` и `go vet ./...`; в корне —
`node --test .github/scripts/sdk-publisher.test.mjs`. Проверить failure/retry и
публикацию в тестовом репозитории по инструкции docs/sdk-releases.md до первого
production-запроса.
